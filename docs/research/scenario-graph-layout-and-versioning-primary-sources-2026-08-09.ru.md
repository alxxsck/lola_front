# Сложный граф сценария: layout, ветки, перемещение и версии

Дата исследования: 9 августа 2026 года.

## Вопрос

Как сделать большой граф действий читаемым и управляемым: уменьшить пересечения и «перестановку» веток, явно показать «Да / Нет / Тайм-аут», безопасно разрешить перемещение узлов, дать нормальную навигацию и позволить менять первое действие без архивации опубликованного сценария.

Ниже сначала зафиксированы факты из первичных источников, затем отдельно — рекомендации для Lola. Рекомендации являются проектным выводом, а не буквальным требованием одной из библиотек.

## Что уже видно в текущей реализации Lola

- Layout в `ScenarioEditorPage.vue` рассчитывается вручную: глубина узла определяет строку, а порядок `form.actions` — колонку. Алгоритм не минимизирует пересечения и не учитывает устойчивый порядок выходов одного ветвления.
- Все узлы передаются в Vue Flow с `nodes-draggable="false"`; соединения также запрещены.
- Есть zoom in/out и fit view, но нет minimap и переключателя блокировки layout.
- Для `ASK_CHOICE` ветка истечения срока создаётся с английской подписью `Timeout`, тогда как другие аналогичные подписи уже русские (`Срок истёк`). Это прямой локальный источник смешения языков.
- По существующему архитектурному контракту `docs/scenario-graph-editor.ru.md` координаты узлов не являются backend-семантикой: граф производен от `form.actions`, а ручные координаты сейчас не сохраняются.

## Факты из первичных источников

### 1. Автоматический layout и пересечения

React Flow не поставляет собственный layout-движок. Его официальное руководство описывает Dagre как простой и быстрый вариант для древовидных направленных графов с небольшой конфигурацией, а ELK — как более сложный, но наиболее настраиваемый вариант с поддержкой разных размеров узлов, подграфов и маршрутизации рёбер. [React Flow: Layouting](https://reactflow.dev/learn/layouting/layouting)

ELK Layered располагает узлы по последовательным слоям, направляет большую часть рёбер в одну сторону, переставляет узлы для уменьшения числа пересечений и умеет учитывать edge labels, порты и ортогональную маршрутизацию. [ELK Layered](https://eclipse.dev/elk/reference/algorithms/org-eclipse-elk-layered.html)

Dagre также является layered-layout для направленных графов и позволяет задавать направление, интервалы между узлами, слоями и рёбрами, размеры edge labels и вес рёбер. Но его собственные design priorities ставят скорость выше поиска оптимального layout. [Dagre: configuration and design priorities](https://github.com/dagrejs/dagre/wiki#configuring-the-layout)

Camunda рекомендует строить процесс в одном направлении чтения, избегать обратных и пересекающихся sequence flows, размещать happy path по прямой центральной линии и визуально симметрично показывать связанные split/join. [Camunda: Creating readable process models](https://unsupported.docs.camunda.io/8.6/docs/components/best-practices/modeling/creating-readable-process-models/)

### 2. Устойчивый порядок веток

ELK может использовать исходный порядок узлов и рёбер как tie-breaker при crossing minimization либо жёстко сохранять порядок модели. Документация отдельно предупреждает о компромиссе: принудительный порядок может дать больше пересечений или менее компактный результат. [ELK: Constraining the model](https://eclipse.dev/elk/blog/posts/2023/23-01-09-constraining-the-model.html), [ELK: Force node model order](https://eclipse.dev/elk/reference/options/org-eclipse-elk-layered-crossingMinimization-forceNodeModelOrder.html)

Для выходов одного узла ELK поддерживает фиксированный порядок портов: при `FIXED_ORDER` каждому порту задаются сторона и `port.index`. Это позволяет не менять местами логически разные выходы между повторными расчётами layout. [ELK: Port index](https://eclipse.dev/elk/reference/options/org-eclipse-elk-port-index2.html), [ELK: Port constraints](https://eclipse.dev/elk/reference/options/org-eclipse-elk-portConstraints.html)

### 3. Подписи «Да / Нет / Тайм-аут»

React Flow позволяет показывать подписи рёбер как SVG-текст или как HTML-элементы поверх рёбер. Поэтому короткие читаемые chips возле начала ветки технически поддерживаются без включения текста внутрь узла. [React Flow: Edge labels](https://reactflow.dev/learn/customization/edge-labels), [React Flow: EdgeLabelRenderer example](https://reactflow.dev/examples/edges/edge-label-renderer)

В BPMN условие относится к исходящему sequence flow, а exclusive gateway выбирает одну из явно определённых веток; default flow задаётся отдельно. Имена потоков используются для объяснения выбора. [Camunda: Exclusive gateway](https://docs.camunda.io/docs/components/modeler/bpmn/exclusive-gateways/)

Тайм-аут — не вариант ответа «Да/Нет», а отдельный событийный исход ожидания. В BPMN interrupting timer boundary event используется именно для timeout-пути, а non-interrupting timer — для напоминания без отмены основного ожидания. [Camunda: Events overview](https://docs.camunda.io/docs/8.7/components/modeler/bpmn/events/)

### 4. Перемещение узлов

React Flow хранит `position` узла отдельно от произвольных данных узла и предоставляет отдельные события изменения позиции/drag. Библиотека также позволяет глобально включать и выключать `nodesDraggable`, соединяемость и интерактивность. [React Flow: Node type](https://reactflow.dev/api-reference/types/node), [React Flow component API](https://reactflow.dev/api-reference/react-flow)

ELK имеет интерактивную crossing-minimization strategy, которая использует ранее рассчитанные позиции для порядка узлов в слое. То есть ручная позиция может быть входной подсказкой layout, а не изменением графовой семантики. [ELK Layered overview](https://eclipse.dev/elk/blog/posts/2025/25-08-21-layered.html)

WCAG 2.2 требует, чтобы действие, выполняемое drag, имело альтернативу одним указателем без перетаскивания. Для сортируемого списка W3C прямо приводит кнопки «выше/ниже» как пример. [W3C: Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)

### 5. Навигация большого графа

Встроенные Controls React Flow предоставляют zoom in/out, fit view и переключение интерактивности. MiniMap показывает весь граф и текущий viewport; её можно сделать pannable и zoomable. `fitView` поддерживает padding, границы масштаба и анимированный переход. [React Flow: Controls](https://reactflow.dev/api-reference/components/controls), [React Flow: MiniMap](https://reactflow.dev/api-reference/components/minimap), [React Flow: FitViewOptions](https://reactflow.dev/api-reference/types/fit-view-options)

### 6. Изменение опубликованного процесса

В Camunda новое развёртывание изменённого процесса регистрируется как новая версия определения. Уже запущенные экземпляры по умолчанию продолжают работать по версии, на которой стартовали, а новые запускаются на последней. [Camunda: Versioning process definitions](https://docs.camunda.io/docs/components/best-practices/operations/versioning-process-definitions/)

Camunda Web Modeler разделяет сохранённые version snapshots и текущий редактируемый latest: сохранённую версию можно просмотреть, сравнить, восстановить как latest или скопировать. [Camunda: Process application versioning](https://docs.camunda.io/docs/components/modeler/web-modeler/process-applications/process-application-versioning/)

Перенос уже активного экземпляра на новую версию — отдельная операция с явным migration plan и ограничениями совместимости; это не побочный эффект обычного редактирования. [Camunda: Process instance migration](https://docs.camunda.io/docs/components/concepts/process-instance-migration/)

## Рекомендации для Lola

### P0. Детерминированный читаемый layout

1. Заменить текущую раскладку «depth + индекс в массиве» на **ELK Layered**. Для текущего DAG это более подходящий вариант, чем Dagre: нужны не только координаты узлов, но и crossing minimization, фиксированный порядок портов, edge labels и ортогональная маршрутизация.
2. Выбрать одно направление и не смешивать его внутри графа. Для широкого desktop-холста предпочтительно слева направо; если продукт сохраняет вертикальный граф, применять те же правила сверху вниз.
3. Передавать в ELK фактические размеры узлов и labels. Задать отдельные интервалы node↔node, layer↔layer, edge↔edge и edge↔label; иначе подпись может пересечь линию или узел даже при правильных координатах центров.
4. Основной путь держать прямым. Ветви должны расходиться в фиксированные lanes и при естественном join сходиться обратно, а не взаимно обмениваться сторонами.
5. Добавить regression fixtures: глубокая линейная цепочка, `Да/Нет/Тайм-аут`, два вложенных вопроса, merge нескольких веток, 30–50 узлов. Проверять отсутствие node overlap, стабильность координат при повторном layout и устойчивый порядок портов.

### P0. Семантика и подписи веток

1. Хранить стабильный тип ветки отдельно от отображаемого текста: например `choice:<optionId>`, `timeout`, `fallback`, `goal`. UI-строка не должна быть идентификатором.
2. Локализовать системные labels централизованно: `timeout → «Тайм-аут»` или `«Срок истёк»`, `fallback → «Иначе»`. Исправить текущий литерал `Timeout` в `scenario-graph.ts`.
3. Для бинарного вопроса показывать реальные названия вариантов из сценария. Использовать «Да / Нет» только если это действительно подписи опций, а не угадывать их по позиции.
4. Помещать label-chip рядом с исходным портом, с непрозрачным фоном и достаточным отступом от линии. У timeout добавить иконку часов и отличимый паттерн линии; цвет использовать дополнительно, а не как единственный признак.
5. Закрепить порядок выходов одного вопроса через `FIXED_ORDER` ports: options в порядке доменной конфигурации, затем timeout. Этот порядок должен быть устойчивым между открытиями и после добавления других узлов.

### P1. Безопасное ручное перемещение

Перетаскивание можно разрешить безопасно, если оно изменяет только presentation state:

- связи, `position` действия, приоритет условий и порядок вариантов не меняются при drag;
- координаты canvas хранятся отдельно от исполняемого scenario payload (локально для пользователя или в отдельном versioned UI-layout документе);
- есть два явных режима: «Авто» и «Ручная раскладка»; кнопка «Выровнять автоматически» предупреждает, что ручные позиции будут пересчитаны;
- auto-layout не запускается после каждого drag и не «отпружинивает» узел обратно;
- при добавлении/удалении узла выполняется incremental layout с предыдущими координатами как подсказкой, либо новый узел размещается рядом и полный перерасчёт запускается явно;
- drag имеет альтернативу: «Выровнять», «Переместить в ветку», «Выше/ниже» или иной click/tap control, если положение несёт пользовательскую функцию;
- в published/read-only можно запретить node drag, но оставить pan/zoom/fit/minimap.

Свободное переподключение рёбер не следует включать одновременно с node drag: это уже изменение бизнес-семантики и требует отдельной валидации DAG, доступных целей и версий.

### P1. Навигация

- Оставить zoom in/out и fit view, добавить процент масштаба и reset `100%`.
- Добавить MiniMap только для графов выше порога размера; сделать её pannable, с различимым viewport и возможностью скрыть.
- Pan должен работать независимо от права редактирования. На trackpad — естественное двумерное перемещение и pinch zoom; на мыши — drag пустого canvas, wheel/controls с предсказуемой настройкой.
- Вызывать fit view после первичного/явного auto-layout, но не после выбора узла или ручного drag, чтобы не терять пространственный контекст.
- Команда «К выбранному действию» должна центрировать конкретный узел без пересчёта layout.

### P1. Первое действие и версии

1. В **черновике** первое действие должно редактироваться так же, как любое другое. Если меняется его тип, операция «Заменить действие» создаёт новый config по схеме нового типа, показывает потерю несовместимых полей и сохраняет исходящий переход только если он валиден.
2. Для **опубликованного** сценария команда должна называться «Создать черновик изменений». Она клонирует последнюю редактируемую конфигурацию, включая первое действие; опубликованная версия остаётся неизменной.
3. В шапке черновика явно показывать: «Изменения затронут новые запуски после публикации». После публикации новые runs используют новую версию, активные продолжают исходную.
4. Не связывать это с архивированием. Архивирование — прекращение/скрытие сценария, а не механизм внесения изменений.
5. Миграцию активных runs, если она когда-либо понадобится, проектировать отдельной административной операцией с preview, mapping и валидацией. Не запускать её автоматически при замене первого действия.

## Предлагаемый порядок работ

1. Исправить системную локализацию timeout и добавить тесты labels/branch identity.
2. Ввести адаптер `scenario graph → ELK graph → canvas positions/routes`, не меняя API payload сценария.
3. Зафиксировать semantic port order и набор сложных layout fixtures.
4. Добавить minimap, percent/reset zoom и сохранение viewport.
5. Разрешить presentation-only drag за feature flag; проверить сохранение/сброс ручного layout и доступную альтернативу.
6. Реализовать `published → editable draft` и «Заменить первое действие» с сохранением версии.

## Что не следует считать доказанным источниками

Источники подтверждают возможности библиотек и устойчивые модели workflow versioning, но не выбирают за Lola конкретное направление графа, интервалы, порог появления minimap или место хранения UI-координат. Эти значения нужно проверить на реальных сценариях и скриншотах desktop/mobile. ELK также не гарантирует математически идеальный drawing для любого графа: ordering, crossing reduction и компактность остаются компромиссом, который необходимо закрепить продуктово значимыми fixtures.
